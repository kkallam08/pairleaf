## Product and scope

Pairleaf reveals an existing answer beside its question in the original PDF. It does not generate an answer or judge whether the source answer is correct. Support question papers and textbooks across subjects, with either (1) separate question and answer PDFs or (2) one PDF containing questions and answers. In the one-PDF mode, detect the answer section and offer page-range correction. Match whole numbered questions, including shared subparts and continuation pages. Use chapter, exercise, and section context to distinguish reused numbers.

The public profile supports clean selectable-text PDFs, including embedded diagrams. New scanned documents and handwriting are outside this release. Existing saved OCR sets can still be read, reviewed, and exported; their answer-range editing is unavailable because it requires recognition. The earlier experimental scan profile is documented in the prototype milestones and [experiments/README.md](experiments/README.md).

## Earlier development milestones

These numbered milestones record the prototype history. Use the MVP stages above for the current implementation order.

1. **Build a checked benchmark and local baseline.** Use the supplied PDF pairs and add non-mathematics material before claiming cross-subject accuracy. Record true question-answer locations and complete reveal regions. Evaluate the current exact-number method, then improve local parsing for plain integers, hierarchical identifiers, changed ordering, page continuations, and section context. **Done when:** the benchmark has verified examples of separate and single-PDF arrangements, ambiguous and missing matches, multi-page answers, and repeated numbers; baseline results are recorded.
2. **Add reliable source matching.** Segment question and answer regions. Rank candidate source regions by structure, numbering, wording, terms, and other relevant evidence. Add an AI-assisted stage for difficult changed-number, order, or wording cases; compare it against the same benchmark. An AI result must point to a real source region. **Done when:** every proposed match has a source location and evidence, while ambiguous cases become suggestions for confirmation or remain unresolved.
3. **Build review and reveal.** Show match evidence before answer content. Keep candidate answers behind explicit preview during review. Let the user confirm or correct a suggestion. Show the whole original answer beside the question, preserve reading position, and support multi-page or multi-region answers. **Done when:** checked examples reveal their complete source answer without neighboring answers and corrections persist for the corresponding documents.
4. **Redesign the interface — completed for both import modes, 2026-11-08.** The compact annotation desk uses a slim tool rail, document tabs, white PDF pages, violet margin markers, sentence-case controls, and concise empty states. File drops, searchable question navigation, review, and the responsive answer pane share the design. Kibo interaction patterns were adapted to vanilla TypeScript. Review-list edge fades follow the shadcn reference. “Answers in this PDF” now enables one-file import and a compact answer-range dialog with optional first/last-page previews. **Verified:** both import modes, reading, reveal, review, range correction, keyboard controls, and mobile layout in Chrome.
5. **Build the local study library — completed 2026-11-14.** Delivered through MVP stages 1 and 2 above. IndexedDB stores PDF blobs and versioned study state; backups preserve the same files and links. Stored OCR settings and recognized regions remain available for existing experimental sessions. Local storage belongs to this Chrome profile/extension installation; export backups before uninstalling or moving to another installation.
6. **Evaluate and deliver the personal/tester version.** Measure wrong automatic assignments, automatic coverage, confirmations per 100 questions, unresolved cases, crop completeness, latency, and cost separately. The initial review-burden target is at most 10 confirmations per 100 questions. Any wrong automatic assignment on the checked release benchmark blocks release; this benchmark cannot prove accuracy on every PDF. Start with free local evaluation. Compare AI on difficult cases with an experimental API-usage ceiling of $10, tracking usage and stopping conservatively before the ceiling. The key is a credential, not prepaid model usage; check existing credits when ready. **Done when:** results, limitations, and regression checks for previously supported PDFs are documented, and a personal/tester build passes them.
7. **Ship a visual-recognition patch — initial Haese subset implemented, moved forward at the user's request.** Bundled Tesseract.js and English data run locally without a helper or API usage. The answer-range dialog enables OCR, a bounded question range, and separate question/answer column counts. Recognition uses printed exercise context, blue margin labels, document-specific digit shapes, and whitespace boundaries. Original answer crops support continuations and same-row answers. All OCR assignments enter review. **Checked gate:** Haese PDF question pages 22–27 and answer pages 485–486 yield 24 proposals for Exercises 1A/1B; inspect all 25 source regions and pass offline recognition, cancellation, restoration, and existing-PDF regressions. **Open coverage:** later chapters, review sets, uneven/mixed columns, other label colors/typefaces, automatic scan answer-section detection, and general handwriting. 8. **Prepare public distribution — follows MVP stages 3 and 4.** The base release works locally. Public AI remains a future decision covering authentication, usage cost, and protected credentials rather than a developer key in the extension.
